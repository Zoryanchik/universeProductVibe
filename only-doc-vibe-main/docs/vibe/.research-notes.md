# Prior-art research: plan-high / build-low workflows

Research for Task 1 of the vibe-onboarding effort. Goal: ground `docs/vibe/workflow.md`
(Task 2) in patterns other Claude Code / Cursor setups already use for "plan with the
strongest available model, implement with a faster model." Sources are GitHub repos/code
found via `gh search` and web articles found via WebSearch. Model wording below is kept
generic on purpose — no vendor/model names hardcoded, since the pairing will change over time.

## Patterns worth adopting

- **Plan-mode gate before any edit.** A skill enters a read-only planning mode and only
  transitions to file edits after the plan is explicitly approved (`ExitPlanMode` used as
  a hard approval gate, not a suggestion). Source: `meganz/android` `.claude/skills/fix-jira-bug/SKILL.md`,
  `gittower/git-flow-next` `.claude/skills/implement/SKILL.md`.

- **The plan file is the single source of truth for the build step.** Once a plan is
  approved, the implementing session does not re-read the original skill instructions —
  everything the build model needs (steps, file list, acceptance checks) must already be
  written into the plan document itself. Source: `SparkDevNetwork/Rock`
  `.claude/skills/convert-block/SKILL.md`.

- **Build model is explicitly forbidden from re-architecting.** Multiple independent repos
  encode "never redesign architecture" / "implement what was specified, never redesign" as
  a standing rule for the faster/execution-tier agent — architecture changes are a stop
  condition that must bounce back to planning. Source: `adityaastro2004/founder-os`
  `.claude/agents/eng-executor.md`, `xenobiasoft/sudoku` `.claude/agents/implementation-engineer.md`,
  `ssong2332/crossWalk` `.claude/agents/reviewer.md`.

- **Build agent is scope-fenced to an explicit file list.** The plan enumerates exactly
  which files may be touched; anything outside that list is out of scope even if it looks
  related. Source: `CodeWithHamzaa/gocart` `.claude/agents/uiux-designer.md`
  ("Never redesign outside the milestone's Files list").

- **Model tier is a named config knob, not a hardcoded model name.** A "model profile"
  setting (e.g. quality / balanced / budget / inherit) is stored in project config and
  swapped per-agent, so the workflow survives model releases without editing every skill.
  Source: `gsd-build/get-shit-done` (`.claude/gsd-core/workflows/settings.md`,
  `.../commands/gsd/set-profile.md`).

- **Task list / phase manifest as the handoff artifact.** Planning writes a checklist file
  with per-item status (pending / in-progress / done); the build step reads it, implements
  only the next pending item, and flips its status — this is the mechanism that lets a
  different model (or a fresh session) resume without re-deriving context. Source:
  `dixus/claudeframework` `.claude/skills/1_implement/SKILL.md`.

- **Tiered planning — not everything needs the gate.** Self-contained, well-defined changes
  (add a button, add a test) skip plan mode entirely; only changes touching architecture,
  state management, or multiple files require the planning gate. Keeps the workflow from
  feeling heavyweight for trivial edits. Source: `logical-mechanism/Peace-Protocol`
  `.claude/skills/implement/SKILL.md`.

- **Session/model handoff doc reconstructed from git, not memory.** A handoff file capturing
  goal, current state, files touched, and the exact next step is written from actual git
  state and file contents (not recalled from conversation), so a different model picking up
  the work starts from verified facts. Source: `www-zaq-ai/zaq`
  `.claude/skills/session-handoff/SKILL.md`.

- **Staged spec pipeline as separate consumable artifacts.** Requirements → design → tasks →
  implementation are written as distinct files, each consumed by the next stage, rather than
  one long-lived chat context — this is what lets planning and implementation happen in
  different sessions (and different models) cleanly. Source: `Pimzino/claude-code-spec-workflow`.

- **One controlled review checkpoint between plan and build.** The strong model produces the
  plan; a review pass (human or the strong model itself) checks it *before* handoff to the
  faster model — this is the single point where missing assumptions, scope creep, or
  over-engineering get caught, since the build model is not expected to question the plan.
  Source: "Why I Let a Strong AI Model Plan Before a Cheaper One Codes",
  https://relaxedcoder.com/blog/why-i-let-a-strong-ai-model-plan-before-a-cheaper-one-codes/
